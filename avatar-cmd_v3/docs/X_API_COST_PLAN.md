# X API の費用 最適化計画（着手前レビュー用）

> 作成: 2026-10-06。きっかけ: 1 週間で $5 のクレジットを消費。
> 単価は利用者から共有された X の現行料金: **Post Read $0.005/件・Post Create $0.015/回・User Read $0.010/件**（コードのコメントにある「Owned Reads $0.001」は前提が古いので見直す）。
> 目標: **1 アバターあたり X API 月 $5〜6（約 900 円）を標準、上限 約 1,000 円**。通常投稿と自分の投稿の分析は止めず、引用探索から先に絞る。

## 1. いま X の読み取りが発生している場所（コードで確認）

| # | 処理 | 場所 | 1 回の読み取り | 頻度 | 問題 |
|---|---|---|---|---|---|
| A | **自分の投稿の指標** | `platforms/x.ts` `fetchMetrics` → `GET /2/users/{id}/tweets`（100 件 × 最大 3 ページ） | 「期限の来た投稿のうち一番古いもの」以降の **自分の投稿をすべて** 返す（最大 300 件）。必要な投稿だけでなく全部に課金される | 公開から 48 時間は 6 時間ごと、その後 14 日目まで 24 時間ごと。どれか 1 件でも期限が来ればアカウント単位で実行（`metrics.ts`） | **最大の原因の可能性が高い**。1 日 2 投稿だと、13 日前の投稿の取得のたびに直近 26 件以上を読み直す。ツリー投稿の 2 件目以降・返信も含まれる。1 投稿あたりの取得回数も約 20 回（6h×8 回 + 24h×12 回） |
| B | **引用候補の探索（タイムライン）** | `fetchTimeline` → `GET /2/users/{id}/timelines/reverse_chronological` | 既定 30 件（`scanPosts`、最大 100） | アカウント設定の「◯時間ごと」または自動化ルール（quote_post）のスケジュール | 件数が多め・回数が多めになりがち。返信は除外しているがリポストは返ってくる（読んでから捨てている） |
| C | タイムラインの投稿者情報 | 同上の `expansions=author_id&user.fields=username,name` | 投稿者の数だけユーザー情報が付く | B と同じ | **User Read（$0.010）として課金される可能性**。必要なのは URL 用のユーザー名だけ |
| D | プロフィール（フォロワー数・画像） | `fetchProfile` → `GET /2/users/me` | User Read 1 件 | 1 日 1 回 | 月 30 件 ≒ $0.30。問題は小さい |
| E | 投稿 | `POST /2/tweets` | Create 1 回（ツリーは件数分） | 投稿ごと | 必要経費 |

**現状の概算（1 アバター・1 日 2 投稿・探索 30 件 × 1 日 4 回の場合）**
- A: 1 日 20〜30 回 × 平均 15 件前後 ≒ 300〜450 Reads/日 → **$1.5〜2.3/日**
- B: 30 × 4 = 120 Reads/日 → $0.6/日（C が課金されていればさらに最大 $1.2/日）
- → **1 週間で $10 以上になりうる**。$5/週は「A が主因、B が次」と考えるのが自然

まず本番で確かめること: **設定 > API コスト >「今月の実績」を用途別にして、`指標取得（X）` と `引用探索（タイムライン）` の読み取り件数を比べる**（台帳には件数が記録されています）。

## 2. 最適化（実装案）

### 2-1. 自分の投稿の指標: 「必要な投稿だけ・決まった時点だけ」読む
- 取得方法を `GET /2/tweets?ids=…`（最大 100 件をまとめて指定）に変更 → **読み取りは指定した投稿の数だけ**。一覧を読み直すのをやめる
- 取得する時点を固定（モードで変える。§3）。BALANCED は **公開から 1h / 6h / 24h の 3 回**（ECO は 6h / 24h、AGGRESSIVE は 1h / 3h / 12h / 24h）
- 各時点の値を **履歴として保存**（今は最新値で上書き）→ 「1h で伸びた投稿」「24h で伸びた投稿」を改善処理（14〜27 日）で比べられる
- ツリー投稿は先頭の 1 件だけ、返信・自動化以外のテスト投稿は対象外
- 1 日 2 投稿 × 3 回 × 30 日 = **180 Reads/月 = $0.90**

### 2-2. 引用候補の探索: 「少なく読んで、上位だけ判定」
- 実行は **決まった時刻だけ**（BALANCED は朝 8 時・夕方 18 時の 2 回、日本時間）。「◯時間ごと」の設定は廃止してモードに統一
- 取得件数は **12 件**（ECO 10 件・AGGRESSIVE 20 件）。`since_id` で続きだけ（実装済み）
- `exclude=replies,retweets` にしてリポストを返させない（読んでから捨てる分をなくす）
- **`expansions`（投稿者情報）を外す**。URL は `https://x.com/i/web/status/{id}` で開ける。表示用のユーザー名は、最終的に候補に残った 2〜3 件だけ **ユーザー情報のキャッシュ** から（無ければ 1 件だけ取得）
- 取得後の流れ: 既に取得・評価・引用した投稿 ID は除外（`QuoteCandidate` で管理済み）→ 軽量モデルで 12 件をまとめて採点（ジャンルとの関連・反応・新しさ・引用する価値）→ **上位 2〜3 件だけ** 既存の判定・引用文の生成へ
- 12 × 2 回 × 30 日 = **720 Reads/月 = $3.60**

### 2-3. ユーザー情報（User Read $0.010）はキャッシュ
- 新テーブル `x_users`（x_user_id・username・name・followers・last_synced_at）。**1〜7 日に 1 回** までしか更新しない
- 自分のプロフィール（フォロワー数・画像）は 1 日 1 回のまま（ECO は 2 日に 1 回）

### 2-4. アバターごとの X API 予算と自動の段階的な縮小
- 予算は **アバターごと・X だけ** で持つ（今の予算は全体・全 API 共通）。既定 **標準 ¥800 / 上限 ¥1,000**（ドル建ての単価を設定の為替レートで円に換算）
- 使用率による自動の切り替え（通常投稿と自分の投稿の分析は最後まで止めない）

| 使用率 | 動作 |
|---|---|
| 〜80% | 選んだモードどおり |
| 80% 以上 | 引用探索を 1 日 1 回に・件数を 10 件に・指標取得を 6h / 24h に |
| 100% | 引用探索・引用投稿の自動作成を停止。通常投稿・自分の投稿の分析は継続 |
| 上限を手動で超えて許可 | 画面のボタンで今月だけ再開（記録を残す） |

- ダッシュボードとアバター画面に **X API の今月の使用量**（Post Reads / Post Creates / User Reads・円換算・予算バー）を表示
- 料金表に X の単価（Read $0.005・Create $0.015・User Read $0.010）を初期値として登録し、台帳で User Read を Post Read と分けて記録する

## 3. モード（アバターごと・既定は BALANCED）

1 日 2 投稿の場合（為替 1 ドル ≒ 158 円で概算）

| | ECO | **BALANCED（既定）** | AGGRESSIVE |
|---|---|---|---|
| 自分の投稿の指標 | 6h / 24h（120 Reads） | 1h / 6h / 24h（180 Reads） | 1h / 3h / 12h / 24h（240 Reads） |
| 引用探索 | 1 日 1 回 × 10 件（300 Reads） | 朝夕 2 回 × 12 件（720 Reads） | 1 日 4 回 × 20 件（2,400 Reads） |
| 引用投稿の上限 | 月 10 回 | 月 20 回 | 1 日 1 回 |
| 通常投稿 | 60 Creates | 60 Creates | 60 Creates |
| プロフィール | 2 日に 1 回（15 User Reads） | 1 日 1 回（30 User Reads） | 1 日 1 回（30 User Reads） |
| **月額の目安** | **約 $3.3（≒ 520 円）** | **約 $6.0（≒ 950 円）** | **約 $14.9（≒ 2,350 円）** |

※ 引用投稿の Create（ECO $0.15・BALANCED $0.30・AGGRESSIVE $0.45）とプロフィールの User Read を含む。AGGRESSIVE は月 5,000 円の商品では原価率が高いため、画面で警告を出す。

## 4. 実装の順番

| 段階 | 内容 | 効果 |
|---|---|---|
| X1 | 指標取得を `GET /2/tweets?ids=` と固定時点（1h/6h/24h）に変更、時点ごとの履歴を保存 | **最大の原因を止める**。単独で大きく下がる見込み |
| X2 | タイムライン: `expansions` を外す・`exclude=replies,retweets`・既定 12 件・決まった時刻（朝夕） | 引用探索の費用を約 1/3〜1/5 に |
| X3 | 料金表に X の単価を初期登録、User Read を分けて記録、アバターごとの X 予算と自動縮小、使用量の表示 | 赤字にならない仕組み |
| X4 | モード（ECO / BALANCED / AGGRESSIVE）の画面と、軽量モデルでの 12 件まとめ採点・上位 2〜3 件だけ判定 | 品質を保って読み取りを減らす |
| X5 | 投稿者情報のキャッシュ（`x_users`） | User Read の削減 |

X1・X2 はすぐ効くので先に出せます。テストは既存のモック（`mockFetch`）で、読み取り件数と送るクエリを確認します。

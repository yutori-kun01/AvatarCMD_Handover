## 1. 指標データの拡充（要件 1 の土台）

### 1-1. 今あるデータの限界
- 閲覧数・反応数は **投稿ごと**（`Content.engagement`）で、公開から 14 日だけ取得（`metrics.ts`）。日別の「アカウント全体の閲覧数」は持っていない。
- 指標取得は X / Threads のみ。note の PV は取っていない（`/api/v1/stats/pv` は note-yutori スキルで実績あり）。

### 1-2. 追加するデータ（DB 移行は追加のみ）

`AccountSnapshot` に列を追加:

| 列 | 意味 | 取得元 |
|---|---|---|
| `views` | その日の閲覧数（インプレッション／PV） | 下表 |
| `engagements` | その日の反応数（いいね・返信・リポスト・引用・シェア） | 同上 |
| `viewsTotal` | 累計値（差分計算用。累計しか取れない媒体のみ） | 同上 |
| `source` | `api_daily` / `post_sum` / `cumulative_diff` / `manual` | — |

| 媒体 | 日別閲覧数の取り方 | 確度 |
|---|---|---|
| Threads | アカウントインサイト `GET /{user}/threads_insights?metric=views,likes,replies,reposts,quotes&since=&until=`（日別の時系列） | 高（公式） |
| X | アカウント単位の公式 API なし → 投稿ごとの `public_metrics.impression_count` の **前回取得値との差分** を日付に計上（`post_sum`） | 中（14 日を過ぎた投稿の伸びは入らない） |
| note | `GET /api/v1/stats/pv?filter=all`（記事ごとの累計 PV・スキ）→ 前日の累計との差分（`cumulative_diff`） | 中（非公式） |
| その他 | 手入力（既存のフォロワー手入力と同じ画面） | — |

- worker の `collectFollowers()` と同じ周期（1 日 1 回）で取る。新関数 `collectAccountInsights()` に分け、`refreshFollowers` から呼ぶ。
- X の差分計上: `Content.engagement` に前回値があるので、`collectMetrics()` で更新するときに増分を `AccountSnapshot`（その日）へ加算する。追加コストなし。
- 反応率 = `engagements / views`（日別・期間）。`summarizeMetrics()` の定義に合わせる。

### 1-3. 時系列 API の一本化
現在、日別集計が 2 か所に重複している:
- `/api/stats`（ダッシュボード: 30 日の投稿・失敗・収益）
- `accountVitals()`（収益分析: 月内の投稿・失敗・収益・フォロワー）

→ `service/timeseries.ts` に **`timeseries({ scope: "all" | "avatar" | "account", id?, range: "7d" | "30d" | "90d" | "month:YYYY-MM", metrics[] })`** を作り、両方から使う。返す系列:

`revenue` / `posts` / `failed` / `followers`（終値） / `followersDelta`（前日比） / `views` / `engagements` / `engagementRate` と、それぞれの **前期間（比較用）**。

## 2. 指標で切り替えるグラフ（要件 2）

### 2-1. 部品
`components/analytics/metric-chart.tsx`（新規）— 上部に指標タブ、下に `ComboChart`（`modes={false}`）。

| タブ | 主系列（形） | 補助系列 | 右軸 | KPI 表示 |
|---|---|---|---|---|
| 収益 | 日別収益（棒・ブランドグラデーション） | 累計（面）・前期間の累計（点線） | 累計 | 期間合計・前期比 |
| フォロワー | 前日比（棒・増は緑／減は赤） | フォロワー数（折れ線） | フォロワー数 | 期間の増減・現在値 |
| 閲覧数 | 日別閲覧数（面） | 7 日平均（点線） | — | 期間合計・前期比 |
| 反応率 | 反応率（折れ線・%） | 反応数（棒） | 反応数 | 期間平均・前期比 |
| 投稿 | 投稿（棒）・失敗（赤棒） | 7 日平均（点線） | — | 件数・成功率 |

- 選んだタブ・期間は URL クエリ（`?metric=followers&range=30d`）に保持し、リロードしても戻る。
- アバター詳細・アカウント詳細でも同じ部品を使う（scope だけ変える）。

### 2-2. ダッシュボードの変更
- 上段 KPI を `収益 / フォロワー増減 / 閲覧数 / 反応率`（各 前期比つき）に変更。KPI カード自体をタブとして押せるようにする（Stripe 方式）。
- 「投稿成功率」「予約中／承認待ち」はシステム欄・サイドバーに既にあるので KPI から外す。
- アバター一覧カードに、フォロワー増減のスパークライン（30 日）を追加。

## 3. プロフィール画像をアバターアイコンに（要件 3）

### 3-1. 取得
`ProfileStats` に `imageUrl?: string` を追加。

| 媒体 | 取り方 | 備考 |
|---|---|---|
| X | `GET /2/users/me?user.fields=public_metrics,profile_image_url` | `_normal` を `_400x400` に置換して高解像度で取る。既存の呼び出しにフィールドを足すだけ（追加課金なし） |
| Threads | `GET /me?fields=threads_profile_picture_url` | CDN の URL は **期限付き** → 必ずダウンロードして保存 |
| Bluesky / YouTube | `avatar` / `snippet.thumbnails` | 後回しで可（優先度は X → Threads → その他） |

### 3-2. 保存・反映
- 取得した画像を `saveMedia()` で `MEDIA_DIR` に保存し、`/media/{name}` の URL を使う（外部 URL を直接表示しない。期限切れ・トラッキング回避）。
- `SnsAccount.profileImageUrl` を追加（アカウント単位）。
- アバターのアイコン = 優先順位 `手動設定 > X > Threads > その他`。`Avatar.avatarImageSource`（`manual` / `account:<id>`）を追加し、**手動で設定した画像は自動取得で上書きしない**。
- 画像のハッシュが前回と同じなら保存しない（毎日同じファイルが増えるのを防ぐ）。
- 表示箇所: ダッシュボードのアバターカード（現在は頭文字の丸）、アバター管理、サイドバーのアバター切替（§6）、投稿画面のアバター選択。共通部品 `AvatarIcon` を作る。

## 4. note 下書き入稿の完成度を上げる（要件 4）

### 4-1. 方針
- **公開（＝取り消せない操作）だけは人が押す** という既存方針は維持。
- ただし「有料ライン・価格・見出し画像・本文画像・タグ」は **下書きの段階で設定まで行う**（下書きなので取り消せる）。既存の `note.ts` のコメント「公開・有料設定は自動では行わない」を「公開のみ行わない」に改める。
- 入稿後、編集 URL と「確認チェックリスト」（画像の位置・有料ラインの位置・価格・タグ）を画面に出す。

### 4-2. 処理の流れ（`note.ts` の `publish` を拡張）
1. `POST /api/v1/text_notes` で空の下書き → `{ id, key }`（実装済み）
2. 本文画像のアップロード（**要検証**: 一般に `POST /api/v1/upload_image`（multipart）で note の画像 URL が返るとされる）→ 本文 HTML に `<figure><img src="…"></figure>` で埋め込む
3. 見出し画像（**要検証**: `POST /api/v1/image_upload/note_eyecatch` に `note_id` と画像）
4. `draft_save` に以下を追加（**要検証**: 項目名は参考記事と、ブラウザで手動保存したときの通信を見て確定する）
   - 有料ライン: 区切り位置の段落 ID（本文 HTML の各要素に振っている `name`/`id` の UUID）を指定する方式とされる
   - 価格・有料／無料の別
   - ハッシュタグ（実装済み）
5. 編集 URL を返す（実装済み）

### 4-3. 原稿側の書き方（Markdown 拡張）
AI に書かせる原稿と、手書き原稿の両方で使える目印を決める:

| 目印 | 意味 |
|---|---|
| `**太字**` | 太字（実装済み。note エディタの太字タグと一致するか **要検証**） |
| `<!-- paywall -->` | ここから有料（この直後の要素の UUID を区切りとして送る） |
| `<!-- image: 説明 -->` | イメージ画像の挿入位置（§5 で生成） |
| `<!-- infographic: 説明 -->` | 図解の挿入位置（§5 で生成） |
| frontmatter `price: 500` / `eyecatch: …` / `tags: […]` | 価格・見出し画像・タグ |

### 4-4. 検証手順（実装前に必ず行う）
1. 参考記事 2 本の内容を、ネットワーク制限のない環境（PC にリンクしたセッション等）で確認する。
2. テスト用の下書きをブラウザで手動作成（太字・画像・有料ライン・価格）→ 開発者ツールで `draft_save` の送信内容を保存。
3. 保存した送信内容を `platforms.test.ts` のテストデータにし、変換結果が一致するかを自動テストで確認。
4. 実アカウントへの入稿は確認を取ってから 1 件だけ。

## 5. 見出しごとのイメージ画像・インフォグラフィック（要件 5）

### 5-1. 2 種類を分けて作る
| 種類 | 作り方 | 理由 |
|---|---|---|
| イメージ画像（見出し画像・各大見出しの雰囲気画像） | **画像生成 AI**（OpenAI の画像モデル / Gemini の画像モデルなど。参照画像を渡せるもの） | 写真・イラスト的な表現が必要 |
| インフォグラフィック図解 | **AI が「図の設計図（JSON）」を作り、プログラムが HTML/SVG で描いて PNG に書き出す** | 画像生成 AI は日本語の文字が崩れやすく、数値やグラフも不正確になりやすい。テンプレート描画なら文字・数値・アイコンが確実 |

※ Claude（Anthropic）は画像を生成しないので、イメージ画像には別の画像生成 API キーが必要。図解の設計（JSON）と、スタイル参照画像の読み取り（画像入力）は Claude を含む既存の LLM 設定で行える。

### 5-2. アバター別スタイルナレッジ
- 新モデル `StyleReference`（`avatarId`, `kind: "image" | "infographic"`, `mediaName`, `note`, `isActive`）。複数枚登録できる。
- 登録時に LLM（画像入力対応）で参照画像を読み、**スタイル定義** を作って保存:
  `{ palette: [...], background, mood, illustrationStyle, lineWeight, iconStyle: "solid" | "outline" | "duotone", fontFeel, layoutDensity, avoid: [...] }`
- スタイル定義は人が画面で修正できる（自動で作った内容をそのまま使わない）。既存の `KnowledgeItem`（`kind: "persona"`）とは分ける（画像を持つため）。

### 5-3. イメージ画像の生成
1. 見出し（h2/h3）と本文の要約 → LLM がプロンプトを作る（スタイル定義・参照画像を添える）
2. 画像生成 API を呼ぶ（参照画像を入力できるモデルなら参照画像も渡す）
3. `saveMedia()` で保存 → 記事の該当位置に紐づけ
4. 使用量を `UsageLedger` に記録（`cost.ts` の料金表に画像の単価を追加）。**月の予算（既存）で止められる** ようにする

### 5-4. インフォグラフィック
- 図の型（テンプレート）を用意: `steps`（手順）/ `compare`（比較・Before→After）/ `cycle`（循環）/ `hierarchy`（階層）/ `stat`（大きな数字）/ `chart`（棒・円・折れ線）/ `checklist`
- LLM には「型・要素ごとのアイコン名・短いラベル（1 要素 12 文字以内などの上限）・数値」だけを JSON で出させる（既存の `completeJson` を使う）
- アイコンは無料・商用可のセットを **パッケージとして同梱**（外部 CDN に頼らない）:
  - Font Awesome Free（CC BY 4.0 / SIL OFL / MIT）
  - Bootstrap Icons（MIT）
  - Lucide（ISC。Web 画面で既に使用）
  - LLM が出したアイコン名は **同梱リストに存在するかを検証** し、無ければ近い名前へ置換
- グラフは SVG で直接描く（数値は JSON から。AI に画像として描かせない）
- 色・太さ・背景はスタイル定義から。フォントは Noto Sans JP（同梱）
- 書き出し: Playwright（Chromium は既に環境にある。`packages/chrome-empire` は未使用なので、描画専用の小さな関数を `integrations` に置く）で 1280×720 / 1080×1080 の PNG
- 「初心者が文字少なめで理解できる」チェック: 1 図あたりの総文字数・要素数の上限を設け、超えたら LLM に作り直させる

### 5-5. 執筆フロー（記事エディタ）
1. テーマ → 構成案（h2/h3 ごとに「画像なし / イメージ画像 / 図解」を AI が提案、人が変更可）
2. 本文生成（既存の `generate` を記事向けに拡張。有料ラインの位置も提案）
3. 画像・図解を生成（見出しごとに再生成・差し替え・削除ができる）
4. プレビュー（note での見え方に近い表示）
5. 「note に下書き保存」→ §4 の処理 → 編集 URL とチェックリスト

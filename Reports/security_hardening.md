# Avatar CMD セキュリティ強化 — 実施内容と運用手順

> 実施日: 2026-11-10
> 対象: avatar-cmd_v3

## 1. 実施した対策

| # | 脅威 | 対策 | 場所 |
|---|---|---|---|
| 1 | Next.js の既知の脆弱性（重大: 画像最適化 API での認証なしのリモートコード実行 GHSA-2464-fhr4-w9xw ほか） | Next.js 15.5.26 → 15.5.29。postcss・source-map-js・postcss-selector-parser を修正版に固定 | `apps/web/package.json`, `pnpm-workspace.yaml` |
| 2 | パスワードの総当たり | 同じ IP の失敗 5 回/15 分でその IP を停止。全体の失敗 50 回/15 分ですべてのログインを停止（IP の偽装対策）。停止中はパスワードを確かめない | `service/admin-security.ts`, `api/auth/login` |
| 3 | パスワードの漏えい | 2 段階認証（認証アプリの 6 桁・RFC 6238）。同じコードの使い回しを拒否。回復コード 10 個（ハッシュのみ保存・1 回限り）。秘密鍵は暗号化して保存 | 同上、設定 > システム > セキュリティ |
| 4 | Cookie の盗用 | サーバー側のセッション（DB には乱数のハッシュだけ）。ログアウト・パスワード変更・「この端末以外をすべてログアウト」で即時に失効。最長 7 日、24 時間操作が無ければ失効 | `lib/session.ts`, `lib/guard.ts` |
| 5 | middleware のすり抜け | middleware（署名・期限）に加えて、すべての API（`route()`）で DB のセッションを確認する二重のチェック | `lib/api.ts`, `lib/guard.ts` |
| 6 | 他サイトからの操作（CSRF） | 書き込み系のリクエストは Origin / Sec-Fetch-Site が自サイトでなければ拒否（middleware と API の両方） | `lib/session.ts` |
| 7 | 内部情報の漏えい | ログイン前に呼べる API では、想定外のエラーの詳細（内部のパス・ライブラリ名）を返さず照会番号だけ返す。`X-Powered-By` を出さない | `lib/api.ts`, `next.config.mjs` |
| 8 | XSS・クリックジャッキング・中間者 | CSP、X-Frame-Options: DENY、HSTS、nosniff、Referrer-Policy、Permissions-Policy、COOP。API の応答は保存させない（no-store）。公開メディアは単独で開いてもスクリプトを動かさず、検索エンジンに載せない | `next.config.mjs`, `app/media/[name]` |
| 9 | 弱いパスワード | 12 文字以上、同じ文字の繰り返しなどを拒否 | `lib/auth.ts` |
| 10 | コンテナを乗っ取られた後の被害拡大 | web・worker・migrate から Linux の権限をすべて外し、権限の昇格を禁止。公開アドレスを `WEB_BIND` で絞れるように | `docker-compose.yml` |
| 11 | 不正アクセスに気づけない | ログイン成功・失敗・停止・ログアウト・パスワード変更・2 段階認証の変更を IP・ブラウザ付きで記録し、画面で確認できる | 設定 > システム > セキュリティ |

すでにあった対策（変更なし）: 認証情報の AES-256-GCM 暗号化、パスワードの scrypt ハッシュ、DB を外部に公開しない構成、非 root ユーザーでの実行、外部 AI 用 API のキーの HMAC 保存・権限・回数制限・監査、内部ネットワークへの接続防止（SSRF 対策）、取り込んだ資料の中の指示に従わない AI のプロンプト設計。

## 2. 確認したこと

- 自動テスト: 全 226 件中 224 件が成功（失敗 2 件は今回の変更前から失敗していた動画パイプラインのテスト）。新しく 6 件追加（TOTP は RFC 6238 の検証用の値と照合）。
- 実際にサーバーを起動して外から試した結果:
  - ログインしていない・偽造した Cookie → 401
  - 6 回目の失敗以降 → 429（停止中は正しいパスワードでも拒否）
  - 他サイトの Origin からの書き込み → 403
  - ログアウト前の Cookie を使い回す → 401
  - 2 段階認証: パスワードだけ → コードを要求、間違ったコード・使い回し → 401
  - セキュリティヘッダーが付いていること、9 画面でブラウザのエラーが無いこと

## 3. 今回は対応していない残りのリスク

| 内容 | 理由 | 対応の目安 |
|---|---|---|
| zod 3（Anthropic SDK・Bluesky の SDK の内部）にメモリを使い切らせる脆弱性 | 修正は zod 4 のみで、SDK が対応するまで上げられない。攻撃者の入力を zod で検証する箇所は無い | SDK の更新時に再確認 |
| deepmerge-ts 7（Prisma のコマンドラインツールの内部） | 起動時・マイグレーション時だけ使われ、外部からの入力を扱わない | Prisma の更新時に再確認 |
| プロキシを通さず直接公開している場合、`X-Forwarded-For` の偽装で IP ごとの制限をすり抜けられる | Next.js の仕様。全体の制限（15 分 50 回）で総当たりは防げる | リバースプロキシ経由で公開する（下記） |
| CSP の script-src に `'unsafe-inline'` | Next.js の初期化スクリプトのため。nonce 方式への移行は全画面の動的描画が必要 | 必要になったら検討 |
| `/media/` は誰でも見られる（ファイル名は推測できない UUID） | Instagram などがこの URL から画像を取り込むため | 個人情報を含む画像を置かない |

## 4. 運用の手順（必ず実施してください）

1. **2 段階認証を有効にする**: 設定 > システム > セキュリティ。回復コードはパスワード管理アプリに保存する。
2. **管理者パスワードを長いものにする**: パスワード管理アプリで 20 文字以上を生成する。
3. **HTTPS のリバースプロキシ経由で公開する**: Traefik 構成（`docker-compose.traefik.yml`）か、同じサーバーの nginx / Caddy から公開し、`.env` に `WEB_BIND=127.0.0.1` を入れて 3333 番を外に出さない。
4. **サーバーの IP 制限**: 管理画面を自分の IP だけに絞る場合も、次は外から届くようにしておく。
   - `/media/`（Instagram・Threads などが投稿の画像・動画を取りに来る）
   - `/api/v1/`（外部の AI から操作する場合のみ）
   - SSH は鍵認証だけにし、パスワードログインを無効にする。
5. **`.env` を守る**: `ENCRYPTION_KEY`・`SESSION_SECRET`・`DB_PASSWORD` は `.env` だけに置き、権限を `chmod 600` にする。Git やチャットに貼らない。
6. **定期的に**: 月に 1 回、`pnpm audit --prod` と Docker イメージの更新、ログイン履歴の確認。見覚えのないログインがあれば、パスワード変更と「この端末以外をすべてログアウト」。
7. **バックアップ**: DB のバックアップは暗号化して別の場所に保存する（中に個人情報・暗号化済みのトークンが入る）。

## 5. 更新時の注意

- このバージョンに更新すると、既存のログインはすべて切れます（Cookie の形式が変わったため）。もう一度ログインしてください。
- マイグレーション `20261111000000_admin_security` を適用してください（Docker Compose では起動時に自動で適用されます）。

# プラットフォーム × ジャンルの傾向と、アバターのエクスポート — 設計書

> 作成日: 2026-11-10
> 対象: avatar-cmd_v3

## 1. 目的

1. **アバターをまたいだ学び**: 今の学習（改善処理・成長アルゴリズム・ルールの評価）はアバター単位で閉じている。
   アバターが 10 体、20 体と増えたときに、「どのプラットフォームの、どのジャンルで、どんな構成の投稿が伸びるか」を全アバター横断で集計し、
   新しいアバターでも初日から使えるようにする。
2. **運用代行からの引き渡し**: 運用代行の契約が終わり、クライアントが自分のサーバー（例: XServer VPS）で使い始めるときに、
   そのクライアントのアバターのデータだけを持ち出せるようにする。運用側のノウハウ（上の横断データ）は渡さない。

## 2. データの区分

| 区分 | 中身 | 持ち主 | エクスポート |
|---|---|---|---|
| ① アバターのデータ | 人格・口調、投稿、指標、ナレッジ（履歴含む）、改善の履歴、成長の状態、自動化ルール、画像スタイル、収益 | クライアント | 含める |
| ② 運用ノウハウ | プラットフォーム × ジャンルの傾向（`PlatformInsight`） | 運用側 | **含めない** |
| ③ 接続情報・秘密 | SNS のトークン、開発者アプリの秘密、AI の API キー、アバターのメールアカウント | クライアント / 運用側 | **含めない**（移行先で接続し直す） |

### 「② を ① にコピーしない」ルール

- 傾向はアバターのナレッジに文章として書き込まない。投稿を作るときに `PlatformInsight` を**その場で読んで**プロンプトに添えるだけにする。
- そのため、エクスポートしたデータには傾向が残らない。移行先では傾向なし（コードの初期値）で動き始め、そのアバター自身の改善処理で学んでいく。
- アバター自身の投稿から学んだこと（改善処理の結果・ナレッジ）は ① なので、そのまま渡す。

## 3. ジャンル（自動判定）とクライアントのラベル

- `Avatar.genre`: 決まった選択肢（`GENRES`）のキー。**自動で判定する**。
  - 判定の材料: 名前・役割・専門分野・想定読者・プロフィール・得意なトピック。
  - AI（用途「ジャンル判定」）に選択肢の中から 1 つだけ選ばせる（JSON スキーマで選択肢以外は返せない）。
  - AI のキーが無い、または失敗したときは、キーワードによる判定（コード）で決める。
  - 材料の内容から作ったハッシュを `genreMeta.basis` に残し、材料が変わったときだけ判定し直す（費用を抑える）。
  - 画面で手動で選ぶこともできる（`genreMeta.source = "manual"`）。手動の値は自動判定で上書きしない。「自動に戻す」で自動判定に戻せる。
- `Avatar.clientLabel`: 任意の文字列。付けても付けなくてもよい。エクスポートでクライアント単位にまとめて選ぶとき、傾向の画面で「何クライアント分のデータか」を表示するときに使う。

## 4. プラットフォーム × ジャンルの傾向（運用ノウハウ）

### 投稿の構成の分類（コード・AI は使わない）

| 分類 | 値 |
|---|---|
| 書き出し（hook） | 問いかけ / 数字 / 言い切り |
| 長さ（length） | 短文: 短い（〜60字）/ 中くらい（〜140字）/ 長い（〜280字）/ とても長い。長文媒体: 〜3000字 / 〜6000字 / それ以上 |
| 形式（format） | 箇条書き / 段落分け（3 段落以上）/ ひとかたまり |
| ハッシュタグ（hashtags） | なし / 1〜2 個 / 3 個以上 |
| リンク（link） | あり / なし |
| 時間帯（time, 日本時間） | 朝 5〜10時 / 昼 10〜17時 / 夕方 17〜22時 / 深夜 22〜5時 |

### 集計の手順

1. 直近 90 日の公開済み投稿のうち、表示回数・反応数が取れていて、指標が出そろう日数（`PLATFORM_PROFILES.settleDays`）以上たってから取得したものを使う。
2. **アバター × プラットフォームごとに「普段」を決める**: 表示回数と反応率の中央値。投稿が 8 件未満なら使わない。
3. 投稿ごとのスコア = （表示回数 ÷ 普段の表示回数 + 反応率 ÷ 普段の反応率）÷ 2。それぞれ 5 倍で頭打ち。
   → アバターの規模・ジャンルによる絶対値の差を消し、「自分比でどれだけ良かったか」だけを比べる。
4. アバターごとに、構成の値ごとのスコアの中央値を出す（その値の投稿が 3 件以上あるときだけ）。
5. プラットフォーム × ジャンル（と「全ジャンル」）ごとに、**アバターごとの値の中央値**を傾向（lift）とする。1 体の投稿が多くても結果を左右しないよう、アバター 1 体を 1 票として数える。
6. **3 体以上**のアバターで同じ値が集計できたときだけ保存する。あわせて「普段より良かったアバターの割合（agree）」を残す。
7. 保存するのは数値だけ（投稿の本文・アバター名は保存しない）。毎日 1 回、全件を作り直す。

### 投稿の生成での使い方（任意・既定はオフ）

- 設定「傾向を投稿の生成に使う」をオンにすると、そのアバターのプラットフォーム × ジャンル（無ければ全ジャンル）の傾向のうち、
  lift が 1.15 以上かつ agree が 6 割以上のものを、分類ごとに 1 つ、最大 3 つまでプロンプトに添える。
- 添える文には「口調・主張・事実は変えない。アバターに合わなければ無視してよい」と明記する。
- まずはオフのまま傾向の画面で中身を確かめ、納得できたらオンにする運用を想定している。

### 今回は作らないもの

- `PLATFORM_PROFILES`（媒体ごとの重み・出そろう日数）を横断データから学習する仕組み。傾向の集計がたまってから検討する。

## 5. エクスポート / 取り込み

### ファイル

- 形式: gzip 圧縮した JSON（拡張子 `.avatarcmd.json.gz`）。
- `format: "avatar-cmd-export"`、`version: 1`、`schemaVersion`（作成元の DB の最新マイグレーション名）を持つ。
- 取り込み側の DB が `schemaVersion` より古いときは、取り込む前に止める（「取り込み先のシステムを更新してください」）。
  古いファイルを新しいシステムに取り込むのは可（無い項目は既定値になる。取り込み先に無い項目は捨てる）。

### 含めるもの / 含めないもの

| テーブル | 扱い |
|---|---|
| Avatar | 含める（Chrome プロファイルの紐づけは外す） |
| SnsAccount | 含める。**トークン・セッション・認証情報は外し、停止中**にする。移行先で接続し直す |
| GrowthState / AccountSnapshot | 含める |
| Campaign / Content / PostMetricSnapshot | 含める。予約中・投稿中の投稿は下書きに戻す（予約投稿 ScheduledPost は含めない） |
| RevenueItem / Revenue / AvatarAnalytics | 含める |
| AutomationRule | 含める。**停止した状態**で取り込む（移行先で確認してから再開する） |
| KnowledgeItem / KnowledgeRevision | 含める |
| StyleReference と参照している画像 | 含める |
| ImprovementCycle / ImprovementSchedule | 含める |
| Collaboration | 両方のアバターをエクスポートするときだけ含める |
| AvatarIdentity | 含めない（パスワードは作成元の暗号鍵で暗号化されていて、移行先では読めないため） |
| AvatarPlatformApp / PlatformApp / AppSetting / ApiKey | 含めない（秘密情報・システム設定） |
| DecisionEvent / QuoteCandidate / ActivityLog / UsageLedger | 含めない（運用の記録） |
| VideoEpisode などの動画パイプライン | 今回は含めない（必要になったら追加する） |
| **PlatformInsight** | **含めない**（運用ノウハウ） |

### ID の付け替え

- 取り込むときはすべての行に新しい ID を振り、関連（アバター・アカウント・投稿・ルールなど）を付け替える。
- JSON の項目（投稿の metadata の `automationId` など）に入っている古い ID も、同じ対応表で置き換える。
- そのため、同じファイルを 2 回取り込むと別のアバターとして 2 体できる（上書きはしない）。

### 画像

- アイコン・参考画像・投稿の metadata から参照しているメディアのファイルを base64 で同梱する（「画像を含めない」も選べる）。
- メディア名は UUID なので、取り込み先に同じ名前があれば書き込まない。

## 6. 画面

- アバター > 編集: 「クライアント（任意）」「ジャンル（自動 / 手動で選ぶ）」。プロフィールのタブに判定結果と理由を表示。
- 設定 > AI 共通・判定 > プラットフォームの傾向: 傾向の一覧（プラットフォーム・ジャンルで絞り込み）、今すぐ集計、生成に使うかのオン/オフ。
- 設定 > AI 共通・判定 > ジャンル判定の AI: ジャンル判定に使うモデル。
- 設定 > システム > エクスポート / 取り込み: クライアントのラベルかアバターを選んでダウンロード、ファイルを選んで取り込み。

## 7. 引き渡しの手順（運用代行の終了時）

1. 移行元: 設定 > システム > エクスポート で、そのクライアントのラベルを選んでダウンロードする。
2. 移行先: Docker が動くサーバー（XServer なら VPS）に同じ版の Avatar CMD を立ち上げ、初期設定をする。
3. 移行先: 設定 > システム > 取り込み でファイルを選ぶ。
4. 移行先: SNS アカウントを接続し直し、AI の API キーを入れ、自動化ルールを確認してから再開する。
5. 移行元: 必要ならアバターを削除する（傾向の集計は数値だけなので、削除後の再集計で自動的に反映される）。

> 運用代行の契約書には、「クライアントの投稿の指標を、個別の投稿が分からない統計として運用側のノウハウに使うこと」を明記しておくのが安全です（表現は専門家に確認してください）。
